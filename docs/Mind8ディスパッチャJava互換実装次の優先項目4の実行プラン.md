# Mind8ディスパッチャ Java互換実装 次の優先項目4の実行プラン

## 目的

C版とJava版に同一のMCOを入力する再実行可能な回帰テストを整備し、関数番号対応、MCOロード、命令実行、再開・終了の互換性を段階ごとに検証する。Java 20でのコンパイルを含む最終受入れ手順を確立する。

## 現状と対象

Java版は `src/mind8dispacher/` に `Main`、`Dispatcher`、`MCodePointer`、`LocTablePointer`、`AccessPointer`、`StackPointer` の枠があり、MCO解析・命令実行・C関数ハンドラーは未実装である。ワークスペースには `javac -encoding UTF-8 -d build src/mind8dispacher/Main.java` のビルドタスクがある。専用テスト基盤やC版ランタイムとの実行環境は着手時に確認し、存在しないものとして前提を置かない。

- Java版: `src/mind8dispacher/`、既存ビルドタスク、追加するテストと固定fixture。
- C版: 通常ユーザーカーネルのビルド・実行手順、同一入力MCO、C版の期待結果。
- 先行項目: 1の関数番号対応、2のMCOローダー、3の命令・再開制御。
- 成果物: 決定的なMCO fixture、比較結果、Javaテストと再実行手順、実装状況の更新。

## 作業手順

1. C版ランタイムの対象構成、ビルド手順、実行方法、必要なカーネルデータを確認する。C版を同じ環境で構築できない場合は、環境・版・入力・生成条件を記録した基準出力を用意する。基準の由来を追跡できない場合は、C版との比較完了とは記載しない。
2. 同一のMCOを両実装へ渡すテスト起動経路を用意する。JavaのMCOパスを引数から指定できるようにし、作業ディレクトリ依存を避ける。診断ログは標準出力の比較を汚さないよう標準エラーまたはテスト用出力先に分離する。
3. テスト基盤を選定する。既存のJDK中心の最小構成と整合させ、必要な依存だけを追加する。ビルドタスクが `Main.java` からソース一式をコンパイルできる前提も確認し、テストソースが通常アプリケーションへ混入しないようにする。
4. 初期fixtureには、同梱MCOまたは新たに生成する短く決定的なhello相当のプログラムを選ぶ。入力の由来、カーネルのVersion/Runtime/Serial、期待する標準出力、文字コード、改行、終了コードを固定する。カーネルSerial不一致のMCOは正常系として扱わない。
5. 必須の観測値を標準出力と終了コードとし、必要性に応じてテスト専用の方法でデータ領域、両スタック、最終Mコード位置、実行命令数を取得する。観測用コードが通常実行時の意味を変えないことを確認する。
6. 先行項目ごとにテスト群を分ける。関数番号の登録整合性、ローダー正常系・異常系・両エンディアン、命令分岐とスタック、再開・終了を独立に検査し、最後に同一MCOによる統合差分テストを行う。
7. 比較時の改行・文字コード・数値表記の正規化はC版仕様に基づき、意味のある差を隠さない。失敗時にfixture、C版結果、Java版結果、終了コード、対象カーネルをまとめて特定できるようにする。
8. 再実行手順を実装状況文書とワークスペースのビルド/テストタスクに記録する。CIが利用可能なら同じ一連のテストを登録し、未実装関数を含まない入力であることを明記する。
9. 最終段階でJava 20のコンパイラを使い、ソース一式をUTF-8でビルドする。既存タスクをそのまま使う場合は `javac -encoding UTF-8 -d build src/mind8dispacher/Main.java` を実行する。追加ソース・テストソースがある場合は、それらも含む正しいコンパイル/テストコマンドを定義し、コンパイラと実行環境のバージョン、終了コードを記録する。

## 検証と完了条件

- 比較時にC版とJava版が同一バイト列のMCOを使用したことをfixture識別子またはハッシュで確認できる。
- 少なくとも一つの決定的な正常系プログラムで、C版とJava版の標準出力および終了コードが一致する。
- 関数番号、ローダー、エンディアン、スタック・再開制御のテストが対象機能ごとに識別でき、失敗時に入力と期待値を追跡できる。
- 破損MCOと互換条件不一致のテストは正常系から分離され、命令実行前に安全に拒否される。
- Java 20のコンパイルが成功し、テスト一式を定めたコマンドで再実行できる。テスト未実施やC版環境不在があれば、完了範囲と制約をレポートに明記する。
- 対応済み機能だけを検証した結果を、ディスパッチャ全体の完全互換の証明として扱わない。

## 依存・注意点

項目1～3の各完了条件を先に満たし、その差分を項目4のテストへ取り込む。Javaコンパイラの検証はこの最終プランの実施時に必須とするが、本プラン資料の作成時には実行しない。基準MCOとC版結果の出所が曖昧な場合は、テストを通した事実と互換性を確認した範囲を分けて報告する。
