# Mind8ディスパッチャ Java互換実装 次の優先項目3の実行プラン

## 目的

C版 `dispatch.c` の命令実行、`setjmp` / `longjmp` による再開・ディスパッチ終了とプログラム終了をJava版で区別し、Mコード位置・LOC参照・データスタック・リターンスタックの状態遷移を再現する。

## 前提と対象

- Java構成書の `Dispatcher.dispatch()` と4種のポインタークラスは枠のみ。命令形式・位置単位・分岐先計算はC版のマクロおよび実処理から確定する。
- C#完了レポートにあるC版照合事項: `setjmp` 初回値0でループ開始、`longjmp(..., 1)` は通常再開、`longjmp(..., 2)` はディスパッチ終了。`FETCH_MCODE` はC関数呼出し前に命令位置を進め、`stackReset()` はMコード位置を戻さない。
- C版: `dispatch.c`、`0ker.c` 等の再開・終了関数、`ptrdef.c` のスタックリセット。
- Java版: `Dispatcher.java`、`MCodePointer.java`、`LocTablePointer.java`、`StackPointer.java` と関数テーブルのハンドラー。

## 作業手順

1. C版の命令取得・符号付き/符号なし判定、C関数番号の抽出、LOC分岐、戻り番地のpush/pop、命令位置の単位を表にする。Javaの `byte` / `short` は符号付きであるため、16ビット命令は `Short.toUnsignedInt` 等で扱い、最上位ビットと下位15ビットの意味をC版に合わせる。
2. `setjmp` 相当の遷移を、継続、初期状態へ戻して再開、現在のディスパッチ終了、アプリケーション終了に分ける。各要求が変更するポインター、スタック、戻り値、プロセス終了コードを定義する。
3. `Dispatcher.dispatch()` を明示的な制御ループにする。JavaではCの `longjmp` を直接再現できないため、状態コードを持つ専用の制御例外または戻り値方式を選び、ハンドラーからの要求が一箇所で解釈される構造にする。通常の実行エラーと制御遷移を混同しない。
4. 再開要求の発行元でC版と同じスタックポインターをリセットし、再開処理側で二重リセットしない。命令位置を巻き戻さず、C版で次に実行される命令から継続することを確認する。
5. 終了要求2は現在のディスパッチ一回だけを抜ける。アプリケーション終了はディスパッチ再開経路と分離し、指定された終了コードを失わず `Main` まで返す。制御例外を広範囲で握りつぶさない。
6. 分岐・関数呼出し・戻りでLOC値やリターンスタック値が不正な場合の境界検査を追加する。C版の有効範囲とJava配列の添字への変換を同じ規則にし、範囲外アクセスを意味不明な実行時例外にしない。
7. 小さなMコードまたは制御単体テストで、通常命令、C関数呼出し、Mind単語分岐、return、再開、ディスパッチ終了、アプリ終了を個別検証する。再開・終了ハンドラーが二重実行されないことも確認する。

## 検証と完了条件

- 命令ビットの判定、C関数番号抽出、LOC分岐先、戻り番地の単位とスタック順がC版と一致する。
- 通常再開後は両スタックが規定の初期状態に戻り、Mコード位置はC版と同じ次命令位置を指す。
- 終了要求2は現在のディスパッチだけを一度終了し、次の命令や再開処理を誤って実行しない。
- アプリケーション終了は再開・正常完了と混同されず、終了コードを保持する。
- 各遷移で命令位置・LOC・データスタック・リターンスタックの期待値がテストで確認され、境界外参照は制御されたエラーになる。

## 依存・注意点

項目2でMコードとLOCの論理値・位置単位を確定してから実装する。項目1の関数対応表を使い、未登録C番号を通常の制御遷移や正常終了として扱わない。Java制御例外を採用する場合、スタックトレース生成コストの最適化は正しい捕捉範囲と意味が確定した後に検討する。
